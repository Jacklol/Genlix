# Категории каталога и характеристики

## Что изменилось

- Разделы: `/catalog/meat`, `/catalog/bird`, `/catalog/beer`, `/catalog/water`.
- Категорийные поля определены в `src/lib/catalog/category-fields.ts`. Они общие для формы товара, фильтров и характеристик на странице товара. Все новые поля необязательные. Цена не добавляется.
- Данные полей сохраняются в существующем `catalog.specs`; названия характеристик — ключи хранения. Не переименовывать их без явной миграции.
- Крепость и IBU используют прежние ключи, повторно вводить уже сохранённые значения не нужно.
- Фильтры строятся только по опубликованным данным. Старые товары без новых характеристик остаются в полном списке, но не проходят фильтр по неизвестному значению. Название товара не разбирается для угадывания характеристик.
- Птица, ранее записанная в мясной категории, также остаётся на странице птицы без дублирования товара.
- HoReCa/ритейл: у мяса поддерживается `channel: "both"`, у остальных категорий — «HoReCa / ритейл». Такой товар подходит обоим фильтрам.
- При смене раздела переносятся только общие фильтры, имеющие соответствующие значения в новом разделе. Вид, упаковка, отрубы и прочие специфические условия сбрасываются.
- URL содержит применённые фильтры. Карточка товара получает проверенный внутренний `returnTo` и ссылку обратно к выбранным товарам.

## Совместимость и безопасность данных

Схема CMS 3 добавляет категорию `water` и двойной канал поставок мяса. Снимки схем 1 и 2 читаются без переписывания и изменения контрольной суммы. Обновление схемы происходит при сохранении товара; прежние версии остаются в истории. Картинки, ID и URL товара не меняются.

В Supabase новые таблицы/колонки и SQL-миграция не требуются: существующий снимок JSONB и RPC поддерживают положительные версии схемы. Проверка ожидаемой ревизии, контрольные суммы, архив и история остаются действующими.

После сохранения схемы 3 нельзя откатывать только приложение на сборку, понимающую лишь схемы 1–2: она откажется читать новые данные. Для аварийного отката нужно использовать совместимую сборку или осознанно восстановить старую ревизию через админку. Это восстановит состояние всей базы на тот момент, поэтому сначала экспортировать свежую резервную копию.

Перед обновлением сделана локальная копия текущей ревизии 12 и её истории в `.data/cms/manual-backups/20260909-catalog-v3/` (не входит в Git). Публичный Supabase и Vercel в рамках этой работы не изменялись. Перед отдельным продакшен-развёртыванием следует экспортировать актуальный снимок из админки продакшена, затем публиковать совместимую сборку.

## Проверки

```sh
node --test scripts/test-category-catalog.mjs scripts/test-meat-characteristics.mjs scripts/test-product-editor.mjs scripts/test-news-editor.mjs scripts/test-home-hero-story.mjs
pnpm exec tsc --noEmit
pnpm build --webpack
```

Тесты создают изолированное локальное хранилище во временной папке без Supabase-переменных; проверяют черновики, публикацию, перезагрузку, архивирование, восстановление, конфликт ревизий, фильтры, старые схемы и неизменность пользовательской базы.
